# ポッドキャストを記事に · podcast-to-article

> このリポジトリは [orange2ai/podcast-to-article](https://github.com/orange2ai/podcast-to-article)（MIT）をフォークし、中国語の文書を日本語に訳したものだ（2026-10-28）。中国語の原文は[元のリポジトリの README](https://github.com/orange2ai/podcast-to-article/blob/main/README.md)、英語版は [README.en.md](./README.en.md) にある。

ポッドキャスト1回分の文字起こしを、そのまま公開できる長文の記事にまとめるスキル。複数人の対談にも1対1のインタビューにも使え、素材は中国語でも英語でもいい。

文字起こしは**誰がいつ話したか**の順に並んでいる。記事は**何の話で、どう考えるか**の順に並べる。このスキルはこの並べ方を組み替える。

![ポッドキャストを記事に: 録音から原稿へ、並べ方を組み替える](./assets/cover.png)

## なぜ必要か

モデルに「文字起こしを記事にして」とだけ頼むと、たいてい次の3つの失敗のどれかになる。

1つ目は話した順に並べるだけの記事だ。「張三は……と言った」「李四は……と言った」「王五は……と言った」が続き、議事録のように読める。2つ目は抽象的にまとめすぎた記事だ。数字や細かい話が全部落ち、「業界は加速している」「エコシステムは成熟しつつある」といった文に置き換わる。文章はなめらかでも、新しい情報が1つもない。

3つ目がいちばん気づきにくい。**書き直しすぎ**だ。本人の言葉が三人称の要約に縮められ、「〜と彼は言う」が消えて、ただの説明文になる。記者が又聞きで紹介しているように読め、その人がどんなふうに話す人なのかが伝わらない。

そこで決まりを3つにした。**発言者ごとの区切りをなくす。細かい事実を残す。本人の話しぶりを残す。** 前の2つは情報を守るため、3つ目は話している人を伝えるための決まりだ。

発言者ごとの区切りをなくすのは、何人かが同じことを話しているときだけだ。1対1の対談では話し手が唯一の情報源なので、反対に、本人の言葉をできるだけそのまま訳して残す。

## 試した結果

話し手ごとに並べた5,730字の原稿が、このスキルの手順で3,703字の公開用の原稿になった。35％短くなり、段落は57から47に減った（数え方はこのリポジトリの `check_style.py` による。字数は中国語の漢字の数）。著者の評価は「大好評」だった。

自己チェックのスクリプトにかけると、ダッシュ、対比構文、まとめ口調、序数詞の小見出し、動詞の名詞化、前の段落を受けずに始まる論評は、どれも0件だった。引っかかったのは「ひとことでまとめると：」という予告のコロンの1か所だけだった。

## 2つ目の事例: 英語の1対1のインタビュー

Invest Like the Best の1回（Noah Shinn が Instinct について話した86分）を中国語の長文にまとめたとき、第1版はまさに3つ目の失敗をした。

初稿は3,600字で、話題ごとに並べただけの43段落だった。1段落は平均84字で、どの段落も言い切りの1文から始まっていた（「安全は2つに分けられる」「変化は3週目に現れた」）。直接の引用は1つもなく、ゲストの言葉はすべて三人称の要約に書き直されていた。著者からは続けざまに3つの指摘を受けた。どの段落も言い切りから始まっている。本筋も話の流れもない。見出しが分かりにくい。

直し方は3段階だった。まず本筋を1つに決めた。この製品はユーザーに代わって自分からお金を使い、取引ごとの手数料で稼ぐ。だからユーザーの側に立たなければならない、という筋だ。本筋に役立たない材料はまとめて削った。次に、要約を本人の言葉に戻し、直接の引用として示した。最後に、各節の見出しを、中身が予想できる文に変えた。

そのあとも3回差し戻された。1回目は、かぎかっこが多すぎるという指摘だった（「原文を多く使えと言ったのであって、全部かぎかっこに入れろとは言っていない。これは読んでいて疲れる」）。2回目は、自分で作ったつなぎの文が重すぎるという指摘だった（「まとめのつなぎは実はすごく単純でいい。たとえば、支払いの話になると、彼は言う」）。3回目は、ゲストの態度を書き手が想像で書いたことへの指摘だった。「この言葉を彼は重々しく言った」と書いたところ、「よい記者はそんな推測はしない」と言われた。文字起こしと照らし合わせ直すと、発言者の取り違えも見つかった。価値観についての段落はまるごとホストの Patrick の発言だったのに、Noah が1人で語ったように書いていた。

最終稿は2,573字になった。直接の引用は全体の23％（18か所）で、言い切りの文から始まる段落は0％。記事のタイトルには Instinct の名前を入れた。

## インストール

```bash
git clone https://github.com/senri1101/podcast-to-article.git
ln -s "$(pwd)/podcast-to-article" ~/.cola/skills/podcast-to-article   # Cola
# ほかのエージェント: ディレクトリごとそのエージェントの skills / rules ディレクトリに置き、SKILL.md を読ませればよい
```

`SKILL.md` はエージェントが読むための説明書だ。特定のプラットフォームには依存せず、python3 の標準ライブラリだけで動く。

## 使い方

エージェントにこう頼む。

> これはこの回のポッドキャストの文字起こしです。Next Token の形式で1本の記事にまとめてください

エージェントは次の7つの手順で進める。文字起こしを整える、要点を整理する、本筋を決める、話題ごとに組み替えて書く（本人の言葉を使う）、名前の出し方を整える、削る、自己チェックをする。

2つのスクリプトは単体でも使える。

```bash
# 字幕の整形: タイムスタンプを消し、話し手ごとに段落にまとめ、統計を出す
python3 scripts/prep_transcript.py 第004回.srt -o 整形稿.md
python3 scripts/prep_transcript.py 第004回.srt --speakers   # 話し手の一覧だけを出す

# 完成稿の自己チェック: AIらしい書き方の項目ごとの件数を、人が書いた文章の基準値と並べて出す
# 直接の引用の割合（インタビュー記事の目安は10〜28％）と、言い切りの文から始まる段落の割合（目安は30％以下）も出す
python3 scripts/check_style.py 完成稿.md
```

対応する形式は SRT、VTT と、md / txt に変換済みの書き起こしだ（`**話し手：**` の印が付いたものも読める）。

> 訳注: `check_style.py` の判定ルールと上の目安の値は、中国語の文章を対象にしたものだ。日本語の原稿にかけても、多くの項目は検出されない。

## 構成

```
SKILL.md                       手順と判断の基準（エージェントが最初に読むファイル）
references/style-rules.md      言葉づかいの決まり。各項目に人とAIの実測値付き
references/example.md          同じ文字起こしを2回まとめた例。元の原稿と完成稿の対照
scripts/prep_transcript.py     字幕の整形
scripts/check_style.py         完成稿の自己チェック
```

## ルールの出どころ

言葉づかいの数値は [lieflat-less-ai-tone](https://github.com/larashero3-dotcom/lieflat-less-ai-tone)（MIT）の研究によるものだ。5つのモデルが生成した文章300本と人が書いた文章329本、合わせて629本（95,551文、45,721段落）を比べ、候補にした26項目の特徴のうち、人とAIを本当に見分けられるものだけを残している。

そのうち3つは、ネットで広まっている説とちょうど逆なので、目を通しておく価値がある。

- 人はAIの **2.4倍** 比喩を使う。人らしく見せようとして比喩を避けてはいけない。
- 本文の中の問いかけは、人が1,000字あたり1.83か所、AIが0.10か所で、**17倍** の差がある。問いかけが少ないほうが、むしろAIらしい。
- 文の長さのばらつきは0.87で、人とAIに**差はない**。文の長さをわざとばらつかせても意味がない。

手順と名前の出し方のルールは、Next Token ポッドキャストの実際の改稿（第4回、Muse の回）から生まれた。「本人の言葉を使う」と「本筋を決める」の2つは、上の英語のインタビューを書き直したときにできた。
