# ポッドキャストを記事に · podcast-to-article

> このリポジトリは [orange2ai/podcast-to-article](https://github.com/orange2ai/podcast-to-article)（MIT）をフォークし、中国語の文書を日本語に訳したものだ（2026-10-28）。中国語の原文は [README.zh.md](./README.zh.md)、英語版は [README.en.md](./README.en.md) にある。

ポッドキャスト1回分の文字起こしを、そのまま公開できる長文の記事にまとめる。複数人の対談でも1対1のインタビューでもよく、中国語の素材でも英語の素材でもいい。

文字起こしの軸は**話し手と時間**で、記事の軸は**話題と判断**だ。このスキルがやるのは、この軸の組み替えだ。

![ポッドキャストを記事に: 録音 → 原稿、一歩で軸を替える](./assets/cover.png)

## なぜ必要か

モデルに「文字起こしを記事にして」とだけ頼むと、出てくるものはたいてい3種類だ。

1つ目は出来事の羅列で、全体が「張三は……と言った。李四は……と言った。王五は……と言った」で埋まり、議事録のように読める。2つ目は抽象化で、数字も細部も全部落ち、「業界は加速している」「エコシステムは成熟しつつある」に置き換わる。なめらかだが、新しい情報は1文もない。3つ目がいちばん気づきにくい。**書き直しすぎ**だ。話し手の言葉が三人称の要約に押しつぶされ、「彼は言う」が平叙文に置き換わり、記者の又聞きの紹介のように読める。その人が話している様子が読み取れない。

だから決まりは3つある。**話し手の足場を外し、事実の粒度を保ち、元の言葉の口ぶりを残す。** 前の2つは情報のため、3つ目は人のための決まりだ。

足場を外すのは、ある条件が成り立つときだけだ。何人かが同じことを話しているときである。1対1の対談では話し手が唯一の情報源なので、逆にできるだけ元の言葉をそのまま訳し、そのまま残す。

## 実際に試した結果

話し手を軸にした5,730漢字の元の原稿が、この流れを経て3,703漢字の公開稿になった。35％削り、段落は57から47に減った（数え方は、このリポジトリの `check_style.py` による）。著者の評価は「大好評」だった。

自己チェックのスクリプトの結果はダッシュ0、対比構文0、まとめ口調0、序数詞の小見出し0、動詞の名詞化0、段落冒頭の前を受けない評言0。「ひとことでまとめると：」の予告のコロン1か所でだけ、一度つまずいた。

## 2つ目の事例: 英語の1対1のインタビュー

Invest Like the Best の1回（Noah Shinn が Instinct について話した86分）を中国語の長文にまとめたとき、第1版はまさに3つ目の誤りを犯した。

初稿は3,600字で、話題ごとに平らに並べた43段落だった。1段落の平均は84字で、どの段落も頭に自己完結した判断の文を1つ置き（「安全は2つに分けられる」「変化は3週目に現れた」）、全体で直接引用は0か所だった。ゲストの言葉はすべて三人称の要約に書き直されていた。著者は立て続けに3つ指摘した。どの段落も頭が断定になっている、本筋も物語らしさもない、見出しが率直でない。

直し方は3段階だった。まず1本の本筋を決めた（それは自分から代わりにお金を使い、取引ごとの手数料で稼ぐ。だからユーザーの側に立たなければならない）。本筋に役立たない材料はまるごと削った。次に要約を元の言葉に戻し、直接引用で示した。最後に、各節の見出しを中身が予想できる文に変えた。

それからさらに3回差し戻された。かぎかっこが多すぎる（「原文を多く使えと言ったのであって、全部かぎかっこに入れろとは言っていない。これは読んでいて疲れる」）。自分でこしらえたつなぎの文が重すぎる（「まとめのつなぎは実はすごく単純でいい。たとえば、支払いの話になると、彼は言う」）。ゲストの態度を代わりに描いた（「この言葉を彼は重々しく言った」と書き、「よい記者はそんな推測はしない」と言われた）。ついでに文字起こしを照らし合わせると、ある段落の発言者を取り違えていたことも分かった。価値観についての段落はまるごとホストの Patrick の発言だったのに、Noah の独白として書いていた。

最終稿は2,573字で、直接引用の割合は23％（18か所）、段落冒頭の自己完結した判断の文は0％。記事のタイトルには Instinct の名前を入れた。

## インストール

```bash
git clone https://github.com/senri1101/podcast-to-article.git
ln -s "$(pwd)/podcast-to-article" ~/.cola/skills/podcast-to-article   # Cola
# ほかのエージェント: ディレクトリごとそのエージェントの skills / rules ディレクトリに置き、SKILL.md を指せばよい
```

`SKILL.md` はエージェントが読む説明書で、それ以外にプラットフォームへの依存はなく、python3 の標準ライブラリだけで動く。

## 使い方

エージェントにこう言う。

> これはこの回のポッドキャストの文字起こしです。Next Token の形式で1本の記事にまとめてください

エージェントは7つの段階を踏む。整形 → 要点の整理 → 本筋を決める → 軸を替えて記事にする（原文を使う）→ 人名の扱い → 削る → 自己チェック。

2つのスクリプトは単体でも使える。

```bash
# 字幕の整形: 時間軸を消し、話し手ごとに段落にまとめ、統計を出す
python3 scripts/prep_transcript.py 第004回.srt -o 整形稿.md
python3 scripts/prep_transcript.py 第004回.srt --speakers   # 話し手の一覧だけ出す

# 完成稿の自己チェック: AIの痕跡ごとの該当数と、人の基準値との対照
# 直接引用の割合（実録スタイルの目安は10〜28％）と、段落冒頭の自己完結した判断の文の割合（目安は30％以下）も出す
python3 scripts/check_style.py 完成稿.md
```

SRT、VTT と、md / txt にすでに変換した書き起こし（`**話し手：**` の印が付いたものも認識できる）に対応している。

> 訳注: `check_style.py` の判定ルールと上の目安の値は、中国語の文章を対象にしたものだ。日本語の原稿にかけても、多くの項目は検出されない。

## 構成

```
SKILL.md                       流れと判断の基準（エージェントの入口）
references/style-rules.md      言葉についての必須の制約。どの項目にも人とAIの実測の基準値付き
references/example.md          同じ文字起こしを2回処理したもの。元の原稿と完成稿の対照
scripts/prep_transcript.py     字幕の整形
scripts/check_style.py         完成稿の自己チェック
```

## ルールの出所

言葉の部分の数値は[lieflat-less-ai-tone](https://github.com/larashero3-dotcom/lieflat-less-ai-tone)（MIT）の対照コーパスの研究によるものだ。5つのモデルが生成した300本と人が書いた329本、合わせて629本、95,551文、45,721段落。26項目の候補の特徴を検証し、本当に区別に役立つものだけを残している。

そのうち3つは、ネットで出回っている説とちょうど逆なので、別に目を通す価値がある。

- 人はAIの **2.4倍** 比喩を使う。「人らしく」見せるために比喩を避けてはいけない。
- 本文での問いかけは、人が1,000字あたり1.83か所、AIが0.10か所で、**17倍** の差がある。問いかけが少ないことのほうがAIっぽさだ。
- 文の長さのばらつきは0.87で、**差がない**。文の長さを無理にばらつかせても意味がない。

流れと人名のルールは Next Token ポッドキャストの実際の改稿の過程（第4回、Muse の回）から来ている。「原文を使う」と「本筋を決める」の2つは、英語の1対1のインタビューのやり直し（上を参照）から来ている。
